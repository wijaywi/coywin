# COYWIN V5: Proof of Steganographic Work (PoSW) and Post-Quantum Ledger Architecture

This document describes the current implementation of the Coywin system. The architecture relies on three primary components: a post-quantum signature verification layer, a deterministic software rasterizer for visual asset generation, and a Proof of Steganographic Work (PoSW) consensus loop.

## 1. Post-Quantum Identity and Ledger (`coywin-ledger`)

Coywin uses `pqcrypto_dilithium::dilithium5` for cryptographic signatures. 

The state is managed locally using the `sled` embedded key-value database. When a transaction is submitted, `verify_gift_transfer` parses a 2592-byte public key and a 4627-byte detached signature. The system explicitly imports `pqcrypto_traits::sign::{PublicKey, DetachedSignature}` to resolve the `.from_bytes()` methods for Dilithium5. If `verify_detached_signature` passes, the `sled` tree is updated with the new owner's key. 

We do not use standard elliptic curves (e.g., secp256k1). Dilithium5 was chosen to provide resistance against quantum algorithms. The current implementation relies on the `pqcrypto` crates, which provide bindings to the reference C implementations.

## 2. Visual Generation Pipeline (`coywin-render`)

The visual output is generated by a deterministic software rasterizer written in Rust. It does not use external graphics APIs (OpenGL/Vulkan) or libraries like Pillow. 

The generator takes a 32-byte block hash and a `nonce` to seed a `ChaCha20Rng`. The PRNG drives the entire generation sequence. 

The geometry consists of two 2.5D Signed Distance Field (SDF) shapes:
- **Orbs**: Rendered via `sdf_circle`.
- **Tapering Cones (Ray-Tubes)**: Rendered via `sdf_cone`, computing the projection factor `h` along a segment from `(ax, ay)` to `(bx, by)`. The radius is linearly interpolated `r = ra + (rb - ra) * h`. The `(bx, by)` coordinate is anchored exactly to the center of a randomly selected Orb, with `rb` sized to a fraction of the target orb's radius (`target_orb.radius * rng.gen_range(0.2..0.5)`). 

Color palettes are selected via `rng.gen_range(0..7)`. Index `5` corresponds to `(0.1, 0.9, 0.3)`, a specific green value chosen for the project. 

The background layer incorporates an additive noise scatter (`add_blend`). The color of the noise is derived directly from a coordinate hash: `((px as u32).wrapping_mul(13579) ^ (py as u32).wrapping_mul(24680)) as f32`. The scatter logic executes before the 3D geometry is alpha-blended on top, forcing the noise into the background depth.

## 3. Consensus and Proof of Steganographic Work (`coywin-node`)

Coywin nodes operate on a custom `libp2p` swarm utilizing `mDNS` for peer discovery and `gossipsub` for block propagation on the `"coywin-blocks"` topic.

The node implements a memory-hard mining loop using `tokio::task::spawn_blocking`. For every `nonce` increment:
1. `block_hash[0]` and `signature[24]` are overwritten with `(nonce % 256) as u8`.
2. The `execute_full_pipeline` routine is called, forcing the `coywin-render` rasterizer to output a full 1920x1080 pixel buffer (over 6.2 million bytes).
3. The raw uncompressed pixel data is hashed using `sha2::Sha256`.

The network difficulty target is currently hardcoded to require two leading zero bytes (`result[0] == 0 && result[1] == 0`). 

By enforcing a 1920x1080 render dimension during the mining loop, the PoSW protocol severely bottlenecks CPU and memory bandwidth. A single hash calculation requires a complete pass of the software rasterizer. We have not benchmarked the exact time-to-block on large networks, but the computational cost per nonce is exceptionally high by design.

## 4. Payload Embedding (`coywin-steg`)

Before the final hash is computed, a cryptographic payload (intended for Plonkish Halo2 zero-knowledge proofs) is embedded into the blue channel of the image. The embedding uses Least Significant Bit (LSB) steganography. 

The implementation uses AVX-512 SIMD intrinsics (`_mm512_loadu_si512`) where supported, falling back to AVX2 or scalar loops. The payload is written by isolating the blue byte of each pixel (`idx + 2`) and modifying the lowest bit (`(b & 0xFE) | bit`). This alters the raw pixel data prior to the SHA-256 difficulty check.
